# 教务适配「后台」调研：怎么给清笺加一所不在 249 名单里的学校

> 2026-10-13 调研。参照系：拾光课程表（`ShiGuangSchedule/shiguang_warehouse`，MIT，Copyright (c) 2025 星河欲转）。
> 这份文档回答两个被混在一起的问题：**① 怎么"适配"一所新教务系统**（写脚本）、
> **② 脚本"存哪 / 怎么分发"**（你说的"后台"）。清笺的短板只在第 ② 个。

---

## 0. 一句话结论

| | 拾光 | 清笺（现状） |
|---|---|---|
| 适配脚本 | 独立 JS，社区贡献 | 同一套 JS（协议已复刻，**能原样跑**） |
| 存在哪 | 远端仓库 `shiguang_warehouse` | **压进 APK** `assets/uniimport/schools/` |
| 加一所学校 | 往仓库 push 一次，App 点「更新仓库」即可 | **必须重新打包发版** |

所以「像拾光那样」= 给 `UniImportPlugin` 补一条**远端适配仓库**通道。
好消息是**最硬的那块骨头（桥协议 + 脚本格式）清笺已经啃下来了**，剩下的只是"下载 + 缓存 + 回退"。

---

## 1. 参照系：拾光的完整机制

### 1.1 仓库结构

```
shiguang_warehouse/
├── index/
│   └── root_index.yaml          # 全部学校/工具的登记表
├── resources/                   # 资源目录，一个文件夹 = 一所学校
│   ├── GLOBAL_TOOLS/            # 通用工具与测试目录（不是学校）
│   │   ├── adapters.yaml
│   │   └── test.js              # ★ 自测占位脚本
│   ├── CUST/
│   │   ├── adapters.yaml        # 该校的适配器元信息
│   │   └── school.js            # 适配脚本本体
│   └── ...
├── proto/
│   └── school_index.proto       # 索引的 protobuf 模板
├── scripts/
│   └── build_data.py            # 把全部 yaml 编译成 school_index.pb
└── .github/workflows/           # CI：自动编译索引
```

### 1.2 两个 YAML 的字段（**全部必填**）

**`index/root_index.yaml`** —— 学校登记表：

```yaml
schools:                 # 固定字段
  - id: "CUST"           # 唯一标识，推荐用域名或全大写缩写（工具用小写）
    name: "长春理工大学"   # 中文名
    initial: "C"         # 首字母，用于排序
    resource_folder: "CUST"   # 资源目录名，建议与 id 一致
```

**`resources/<目录>/adapters.yaml`** —— 适配器元信息（一所学校可挂多个适配器，如本科入口 + 研究生入口）：

| 字段 | 说明 |
|---|---|
| `adapter_id` | 唯一标识，建议 `学校id + 序号` |
| `adapter_name` | 中文名（显示在学校名下面的那行小字） |
| `category` | `BACHELOR_AND_ASSOCIATE` / `POSTGRADUATE` / `GENERAL_TOOL` |
| `asset_js_path` | 脚本的**相对路径**，如 `school.js` |
| `import_url` | **登录页** URL（教务必填，工具可空） |
| `maintainer` | 维护者署名 |
| `description` | 简要说明 |

> ⚠️ 字段不能多也不能少，`import_url` 必须填**登录页面**而不是课表页。

### 1.3 分发：索引编译 + 拉取

- CI（`.github/workflows/build-index.yml`）跑 `scripts/build_data.py`，把全部 yaml **编译成一个
  `school_index.pb`**，推到**孤立分支 `index-pb-release`**（当前索引协议 **v2**）。
- **App 只需要拉两样**：`school_index.pb`（索引）+ `resources/` 下所有 `*.js`。
- 拾光 App 内置「开发者功能」：在「我的-更多」页点图标 5 次打开 → 选**自定义仓库或私有仓库**
  → 拉取更新。这是它做 Beta 验证的方式，也是"后台可换"的证明。

### 1.4 贡献流程：怎么把一所学校"存到后台"

```
Fork 仓库
  → 在 index/root_index.yaml 登记（先登记，否则提交不会被接收）
  → 在 resources/ 建与 resource_folder 同名的文件夹
  → 写 adapters.yaml + 适配脚本
  → 推到自己的分支，充分自测
  → 提交 PR 到上游 pending 分支 → 审核 → 合并进 main
```

三条踩坑提示（官方 README 明写）：

1. ⚠️ **`main` 已开分支保护** —— PR 只能提到 `pending` 分支，等同步。
2. ⚠️ **不改索引，改任何 yaml 都不生效**（yaml 要被编译进 pb 才生效）。所以自测阶段用
   `GLOBAL_TOOLS/test.js` 占位：把代码写进 `test.js`、`asset_js_path` 指向它，就能不更新索引直接测。
3. ⚠️ **别把自测用的 `test.js` 提交上去。**

### 1.5 适配脚本的接口（★ 清笺已 100% 复刻）

脚本被注入到**已登录的教务页面**里执行，通过两个全局对象和 App 通信：

**异步（返回 Promise，await 使用）—— `window.shiguangBridgePromise`**

| 方法 | 作用 |
|---|---|
| `showAlert(title, content, confirmText)` | 公告弹窗，返回 `true/false` |
| `showPrompt(title, tip, defaultText, validatorFnName)` | 输入框（如学年、验证码），返回字符串或 `null` |
| `showSingleSelection(title, itemsJson, defaultIndex)` | 单选（选学期），返回索引或 `null` |
| `saveImportedCourses(jsonString)` | **提交课程数据** |
| `savePresetTimeSlots(jsonString)` | 提交节次时间 |
| `saveCourseConfig(jsonString)` | 提交课表配置（学期开始日 / 总周数等） |
| `saveComboSchedule(jsonString)` | 组合作息方案（**清笺暂不支持，会明确拒绝**） |

**同步 —— `window.shiguangBridge`**

| 方法 | 作用 |
|---|---|
| `showToast(msg)` | 底部提示 |
| `notifyTaskCompletion()` | **流程完全成功的收尾信号**（只有成功才调） |

**课程数据字段（脚本必须解析成这个形状）：**

```json
[{
  "name": "高等数学", "teacher": "张教授", "position": "教101",
  "day": 1, "startSection": 1, "endSection": 2,
  "weeks": [1,2,3,4], "credit": 2.5
}]
```
（`isCustomTime` + `customStartTime/customEndTime` 可选，用于不按节次的课。
`color` / `remark` 是 App 内部字段，脚本给了也不生效。）

**脚本骨架（官方推荐写法）：**

```js
async function runImportFlow() {
  window.shiguangBridge.showToast('导入即将开始…');
  const ok = await window.shiguangBridgePromise.showAlert('提示', '请先确认已登录', '好的');
  if (!ok) return;                                    // 用户取消 → 立即退出
  const year = await getAcademicYear();               // 封装：showPrompt
  if (year === null) return;
  const courses = await fetchAndParseCourses(year);   // 直接在同源页面里 fetch 教务接口
  if (!courses) return;
  await window.shiguangBridgePromise.saveImportedCourses(JSON.stringify(courses));
  window.shiguangBridge.notifyTaskCompletion();       // ★ 只在成功后调
}
runImportFlow();
```

**关键点**：脚本是在**已登录页面的同源上下文**里跑，所以可以直接 `fetch` 教务自己的接口、
复用页面的 cookie —— 这正是"任何来源都能适配"的原因，也是为什么清笺的 WebView 要开
`setDomStorageEnabled` / 接受第三方 Cookie（见 `UniImportPlugin.showDialog`）。

## 2. 清笺现状对照

| 环节 | 拾光 | 清笺 | 差距 |
|---|---|---|---|
| 脚本格式 / 桥协议 | 原始 | **完全一致**（`bridge_init.js` 复刻 + `UniImportPlugin` 实现同一套 action） | ✅ 无 |
| 脚本来源 | 远端仓库 | `assets/uniimport/schools/`（249 所 / 270 适配器 / 3.55 MB） | ❌ 无远端通道 |
| 学校清单 | `school_index.pb`（拉取） | `schools.json`（`listSchools()` 从 assets 读） | ❌ 无远端通道 |
| 更新方式 | App 内「更新仓库」 | 重新打包 APK | ❌ |
| 网络能力 | — | 已有 `INTERNET` 权限；「检查更新」已在用 `fetch(api.github.com)` + 镜像回退 | ✅ 有现成范式 |

**结论**：清笺唯一缺的是 **"从远端拉清单和脚本 → 存本地 → 优先用远端"** 这一段。

## 3. 三条可选路径

| | 路径 A：只提上游 | **路径 B：自建远端仓库（推荐）** | 路径 C：B + 用户自助提交 |
|---|---|---|---|
| 做法 | 把新适配 PR 给 `shiguang_warehouse`，清笺下次打包带上 | 建 `HertaSta/QingJian-Adapters`，App 内「更新学校列表」拉取 | 在 B 上再加 App 内「提交学校」入口 |
| 加学校后 | 要等清笺发版 | **push 一次 + 用户点一下，免重装** | 同 B，且可众包 |
| 开发量 | 0 | 中（插件 + 前端 + 一套合并逻辑） | 大（还需服务端 / Issue 模板 + 审核） |
| 可控性 | 低（上游审核说了算） | 高 | 高 |
| 风险 | 无 | 远程脚本执行 → 需签名校验 | 同上，且审核成本高 |

> 路径 A 不是"不做"，而是**顺带做**：清笺本就是从上游拉数据，我们写的适配提交上去，
> 既帮了社区，清笺下次打包也自动带上。**真正的"后台"要靠 B。**

## 4. 推荐方案：路径 B 详细设计

### 4.1 后台（仓库）长什么样

复用清笺已有的 `schools.json` 格式，**不引入 pb / protobuf**（清笺没有解析 pb 的代码，
而 JSON 索引 91 KB，拉取成本可接受）：

```
QingJian-Adapters/                 （公开仓库，MIT 或与清笺一致）
├── remote.json                    # 版本清单：{ version, updated, count, files: {path: sha256} }
├── schools.json                   # 与现有格式完全一致的索引 [{id,name,initial,sub,url,script,desc,cat,by}]
└── schools/
    └── <folder>/<script>.js       # 适配脚本，与 APK 内目录结构一致
```

- `remote.json` 里的 `files` 给出每个脚本的 **sha256**，App 下载后逐文件校验；
  已存在且 sha256 相同的**跳过下载**（增量更新）。
- 「其他学校」——用户自己填网址选类型的那条路，天然就支持任意教务系统，
  不依赖这个后台。

### 4.2 App 侧要改的地方

**插件 `UniImportPlugin.java`：**

1. 新增 `@PluginMethod syncRemote(call)`：
   - `fetch remote.json` → 对比本地缓存的 __版本__ → 有更新则拉 `schools.json` 与缺失的脚本；
   - 落盘到 **app 私有目录**（`getContext().getFilesDir()/uniimport/schools/`，**不是** assets，assets 只读）；
   - 返回 `{ updated: n, total: m, version }` 给前端展示。
2. `listSchools()` 改为：**先读私有目录的 `schools.json`，没有再回退 assets**。
3. `loadAssets(scriptId)` 改为：**先查私有目录 → 再查 assets**（两层都是同样的查找逻辑，
   现有代码只需把 `readAsset()` 换成 `readFile(path)` 的第一优先级）。

**前端 `index.html`：**

- 学校面板 `#sheetUni` 顶部（或设置页）加一个「更新学校列表」按钮，展示进度 / 结果 / 时间。
- 拉取失败静默回退，不影响内置 249 所的使用。
- 也许在关于页显示「远端清单版本 vs 内置版本」。

**存储与回退：**

```
FilesDir/uniimport/
├── schools.json          ← 远端覆盖层
└── schools/<folder>/*.js
```
查找顺序：`FilesDir` → `assets`。远端文件损坏/缺脚本时自然落到内置版本，**不会白屏**。

### 4.3 合并与去重规则

- **按 `id`（adapter_id）合并**，远端同 `id` 覆盖内置（便于紧急修脚本）；
- 远端**不会删除**内置学校 —— 内置永远是"保底集合"；
- `schools.json` 里带一个 `remote: true` 标记，前端可以（可选）标出"来自更新"。

### 4.4 失败回退

- 网络不通 / 校验失败 → 保持现状，提示「更新失败，仍使用内置列表」；
- 镜像回退：直接复用「检查更新」那套 `UPDATE_MIRRORS` 思路（`ghfast.top` / `ghproxy.net` …），
  先用 `raw.githubusercontent.com`，不通再走镜像。

## 5. 安全红线（必读）

**拉回来的脚本会被注入到教务页面里执行 —— 这是不折不扣的远程代码执行。**

1. **只认自己的仓库**：仓库地址写死在代码里，`syncRemote` 不接受任意 URL（拾光允许填自定义仓库
   是给开发者用的，普通用户不该有这入口）。
2. **sha256 逐一校验**，校验不过直接丢弃该文件。
3. **HTTPS + 域名白名单**（`raw.githubusercontent.com` 及已知镜像）。
4. **必须用户显式点击**才更新，更新后展示"新增了哪些学校"。
5. **不保存任何凭据**这条既有承诺不受影响（脚本跑在校园页面里，清笺仍然不碰账号密码）。
6. 建议：**后台仓库加 CI**，push 时校验每个 `adapters.yaml` 字段齐全 + 脚本能通过语法检查
   （对应上游的 `build-index.yml` 思路）。

## 6. 实操：现在要给一所新学校写适配，怎么做

1. **认系统类型**：正方（zhengfang）/ 青果（qingguo）/ URP / 强智 / 超星（chaoxing）……
   清笺 `assets/uniimport/` 已内置这四套通用脚本（`zhengfang.js` / `chaoxing.js` / `qingguo.js` / `urp.js`），
   先在 `shiguang_warehouse/resources/` 里搜同类学校的脚本，**照抄改选择器/接口地址**，不要从零写。
2. **确认登录页 URL**：填到 `import_url`（注意是登录页，不是课表页）。
3. **拿现成脚本自测**：
   - 最省事：直接在清笺 App 里用「其他学校」→ 选类型 → 填网址跑一遍；
   - 严谨点：用拾光的浏览器测试插件 / 在 PC 浏览器 DevTools 里跑脚本，看输出的 JSON 对不对。
4. **登记**：`root_index.yaml` 加学校，`resources/<folder>/adapters.yaml` 加适配器。
5. **两条去向**：
   - **提上游**：PR 到 `shiguang_warehouse` 的 `pending` 分支 → 合并后清笺下次打包自动带上；
   - **进自己的后台**：把 `schools.json` 加一条 + 脚本放进 `QingJian-Adapters`，用户点「更新」即可。

> 注意：清笺的 4 套通用脚本当初就是从上游搬的，**上游脚本可以直接在清笺跑**——
> 这意味着"提上游" 和 "自建后台" 的内容其实是**同一份产物**，两条路可以并行。

---

## 7. 建议的落地顺序

1. **先做「其他学校」的体验**（已有）：用户能自己填网址选类型 —— 这是**零后台的兜底**，覆盖面最大。
2. **路径 A（提交上游）**：遇到新学校就顺手提 PR，零成本。
3. **路径 B（自建远端仓库）**：等"内置 249 所不够用"成为真实痛点时再上，工作量约
   插件 1 个方法 + 前端 1 个按钮 + 一层查找回退，**不需要服务端**（GitHub 静态仓库就够）。
4. 路径 C（用户自助提交）只在有真实用户量后再考虑。

---

## 附：本次调研的结论摘要

- 拾光的"后台"= **GitHub 仓库 + CI 编译索引 + App 拉取**，本质是**静态托管**，不需要服务器。
- 清笺与拾光的**脚本/桥协议 100% 兼容**，这是最大的现成资产。
- 清笺缺的只是 **远端拉取通道**；补上后"加一所学校不用重发 APK"即可成立。
- **「其他学校」入口已经能覆盖任意教务系统**，自建后台是"体验优化"而非"能力补齐"。
